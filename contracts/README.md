# Contracts

Shared data contracts between the emulator, onboard, Earth, and web. Changes go through an announced PR (see [docs/plan.md](../docs/plan.md)).

| File | Owner | Contents |
| --- | --- | --- |
| [crew.json](./crew.json) | Matheus | The 4 crew members, their wearable binding, and fixed baselines per metric |

## crew.json

All values are **simulated**. They are not clinical reference values.

- `metrics`: the metric IDs used everywhere (observations, alerts, API, UI), with their observation unit, source, and bounded `scale` when there is one. This list stands in for the metric catalog until `contracts/metrics.json` exists; when it does, the IDs and units must match.
- `crew[]`: `crewId`, display data, `deviceId` (the ID onboard sends in each `SyncRequest`), and `baselines`.
- `baselines[metricId]`: `median` and `spread` in the metric's unit.

The deviation from the baseline is:

```text
z = (value - median) / spread
```

`spread` is a robust standard deviation (1.4826 × MAD of the pre-flight days). Questionnaire metrics use a floor of 1 scale point, because their MAD is often 0.

### Units

Observations use human units, not the emulator's integer encodings. Onboard ingest converts:

| Emulator field | Observation metric | Conversion |
| --- | --- | --- |
| `heartRateBpm` | `heart_rate` (bpm) | none |
| `spo2HundredthsPercent` | `spo2` (%) | ÷ 100 |
| `temperatureHundredthsCelsius` | `body_temp` (°C) | ÷ 100 |

The other wearable metrics (`hrv_rmssd`, `resp_rate`, `sleep_duration`, `exercise_duration`) are not generated by the emulator yet.

### Calibration with the emulator

Wearable baselines are tuned to the emulator's ranges, so a single-reading rule with |z| ≥ 3 behaves as expected:

| Scenario | Emulator range | Result |
| --- | --- | --- |
| `NORMAL` | HR 60–95 bpm, SpO₂ 96–100%, temperature 36.0–37.5 °C | \|z\| < 3 for every crew member — no alert |
| `ELEVATED_HEART_RATE` | HR 130–180 bpm | \|z\| ≥ 5 — alert |
| `LOW_SPO2` | SpO₂ 85–92% | \|z\| ≥ 5 — alert |

If the emulator ranges change, update `EMULATOR_RANGES` in the test and re-check the baselines.
